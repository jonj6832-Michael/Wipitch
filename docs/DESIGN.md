# WiPitch — 網頁版單音修音工具

## Context

現有的 `pitchmark.py` 是一個終端機工具：手動標 in/out point、手動填半音數、產生 Rubber Band 的 `.pitchmap` 檔、呼叫 `rubberband` CLI 算繪。它能移動音高，但看不到波形、看不到音高、每次試聽都要等 render。

目標是做一個 **Flex Pitch / Melodyne（單音模式）的替代品**，跑在瀏覽器裡：畫出波形、畫出偵測到的音高曲線、用滑鼠圈選任意一段直接上下拖曳改音高、即時試聽、每個編輯都從原始音檔重算。不做自動音符切割。

### 已確認的決策
- **純瀏覽器 WASM**，不要 Python 後端
- **自由選取**，不做音符切割、不做半音吸附
- 第一版範圍：波形 + 音高曲線 + 拖曳改音高 + 即時 preview + 壓平抖音滑桿 + 音量調整 + 專案存檔 + 匯出 WAV
- **保留音色（formant）是必要功能**，不是加分項——等同現有的 `PRESERVE_FORMANT`（`pitchmark.py:123`）
- 專案打算開源，**GPL 可接受**——spike 實測後確定採用 Rubber Band，所以整個專案是 GPL

## 核心設計：單一「音高偏移曲線」

**原始 audio 永遠不動。** 所有編輯狀態就是一條 Δ(t) 陣列——每 16ms 一格的半音偏移量。

```
原始 AudioBuffer ──┐
                   ├──► Rubber Band (realtime) ──► 輸出
Δ(t) 半音偏移曲線 ──┤     (逐 block setPitchScale)
F(t) formant 曲線 ──┘     (逐 block setFormantScale)
G(t) 增益曲線（dB）──────► 直接乘
```

這一個決定同時解掉所有需求：

| 功能 | 曲線運算 |
|---|---|
| 拖曳一段改音高 | `Δ[a:b] += k` |
| 壓平／放大抖音 | `Δ[t] += (α−1)·(m[t] − c[t])` |
| 音量調整 | `G[a:b] += g`（dB 是加法） |
| 主動調 Formant | `F[a:b] += k`，餵 `rubberband_set_formant_scale()` |
| 畫筆 | 把一段的曲線值直接改寫成畫出來的形狀 |
| 人工 vibrato（將來） | `Δ[t] += A·sin(2πft)` |

（保留音色不在此表——它不是曲線編輯，是算繪器的常駐選項 `FormantPreserved`。
F(t) 是「在保留的基礎上再主動移動音色」。）

其中 `m[t]` 是偵測到的音高（轉成 MIDI 半音刻度），`c[t]` 是 `m` 的平滑中心線。

**「每個編輯都從最初 audio 算起」自動成立**：曲線本身就是完整的編輯狀態，render 永遠是 `原始音檔 + 當前曲線`，不會疊加 artifact。undo 就是 snapshot 整條曲線（沿用 `pitchmark.py:497` `Session.snapshot()` 的做法）。

### 壓平抖音的關鍵細節

`c[t]` 用**移動中位數**，不是整段的常數中位數，否則連刻意的滑音（melodic glide）
也會被壓平。window ≈ 200ms 時：vibrato 是 4–7 Hz 會被濾掉，旋律走向是 <1 Hz 會被保留。

**但視窗長度要跟著 α 走**（使用者實際要的語意）：

| α | 中心線視窗 | 結果 |
|---|---|---|
| ≥ 1 | 200ms | 放大的是抖音，不是整條旋律 |
| 0.5 | 介於兩者 | 抖音減半，刻意的滑音還在 |
| **0** | **整個選取範圍** | 中心線退化成常數 → **整段變成同一個音高** |

只用固定 200ms 的話，α=0 只會貼齊那條「跟著旋律走的中心線」，
框三秒鐘不會得到一個乾淨的長音——那才是使用者要的東西。

移動中位數的視窗在陣列邊緣要**往內推**而不是被截短，否則 window = 整段長度時，
頭尾算出來的仍然是局部中位數，α=0 壓不成一條真正的水平線。

滑桿 α 的範圍：`0` = 整段同一個音高、`1` = 原樣不動、`4.0` = 抖動放大四倍。
選區邊界套 raised-cosine 淡入淡出（≈30ms，等同現有的 `RAMP_MS`），避免接縫爆音。

## 技術選型

### 音高偵測：SwiftF0
- ONNX 模型約 400KB，MIT 授權，可在 onnxruntime-web 跑
- 16 kHz mono 輸入，hop 256 samples = **16 ms 一格**（正好就是曲線的格點）
- 範圍 46.875 Hz – 2093.75 Hz（G1–C7），輸出 pitch + confidence + voicing
- 對此用途最關鍵的優勢是**輸出曲線平滑**（CREPE / pYIN 是鋸齒狀，會讓壓平功能失效）
- 用途僅限「畫 piano roll」與「壓平抖音的中心線計算」。**不要**拿去餵算繪器的 formant 分析（見下）

### 音高處理：Rubber Band WASM（spike 實測後定案）

npm `rubberband-wasm` 3.3.0，完整 Rubber Band 3.3 C API。**GPL，使用者已確認可接受。**

必用 **realtime 模式**：時變音高曲線在 Rubber Band 只能靠 realtime 模式逐 block 呼叫
`rubberband_set_pitch_scale()`（離線模式的 pitch scale 整段固定）。這正是 `pitchmark.py:715`
註解講的「`--pitchmap` 會強制進入 realtime 模式」。

選項組合：`ProcessRealTime | EngineFiner | PitchHighQuality | FormantPreserved`
（等同命令列 `-3 -F`）。

**實測代價：約 5 倍即時速度。** 1 秒 tile 加 0.5 秒 pre-roll ≈ 300ms 算完。
不是瞬間，但可接受。

## Spike 實測結果（已完成，程式在 `spike/`）

測量方法：比較移調前後「頻譜包絡重心」移動了幾個半音。0 = 音色完全沒被移動（完美保留）。
只分析素材中間 4 秒以避開 start delay。0 半音對照組三個引擎都量到 ≈0，指標可信。
素材：`Vocal.wav` 45–53s，女聲，f0 中位數 361Hz。

**formant 偏移量（半音，越小越好）**

| 半音 | Signalsmith | **RB 即時（採用）** | RB 離線（參考上限） |
|---:|---:|---:|---:|
| 對照 0 | −0.00 | −0.15 | +0.00 |
| −7 | **−0.30** | +1.08 | −1.02 |
| −5 | **−0.35** | +0.90 | −0.73 |
| −2 | −0.67 | **+0.33** | −0.12 |
| +2 | **+0.14** | +0.34 | +0.35 |
| +5 | +1.26 | **+0.63** | +0.66 |
| +7 | +2.34 | **+0.70** | +0.66 |
| **平均** | 0.84 | **0.66** | 0.59 |
| **速度** | 44x 即時 | 5x 即時 | 6x 即時 |

結論：
1. **Rubber Band 整體較好**，尤其大幅升調（+7 時 0.70 vs 2.34）——那正是花栗鼠感最明顯的地方。
2. **RB realtime 升調時跟離線幾乎一樣好**，所以「只能用 realtime」沒有犧牲品質；只有大幅降調較差。
3. Signalsmith 降調反而較好，但差距不足以推翻選擇。

### ⚠️ 已推翻的假設：不要餵自己算的 f0 給 formant 分析

原計畫寫著「我們有 SwiftF0，餵準確基頻進去品質會更好」——**實測是反的**。
Signalsmith 的音色保留率：

| formantBaseHz 設定 | 保留率 |
|---|---|
| `0`（library 自己測） | **69%** |
| 逐 frame 餵 f0 | 57% |
| 平滑 0.5s / 2s | 58% |
| 固定中位數 | 60% |

已確認不是追蹤器的問題（八度錯誤僅 1.6%），各種平滑程度結論一致。
**一律讓算繪器自己偵測基頻。** 好消息是這讓架構更單純：偵測層與算繪層完全解耦。

### 從 OpenTune 學到的（AGPL，不抄程式碼，只借架構觀念）
OpenTune 用 **RMVPE 偵測音高 + PC-NSF HifiGAN 神經聲碼器重新合成**，這是它宣稱大幅度移調仍自然的原因。

- **不採用 RMVPE**：ONNX 模型 **362 MB**，瀏覽器首次載入不可行（SwiftF0 是 400 KB）。
- **要借的架構觀念**：把算繪器抽成介面 `Renderer { render(audio, deltaCurve, gainCurve) }`。
  這在 spike 之後更顯重要——我們已經實際換過一次引擎了。

## 實作

### 技術堆疊
Vite + TypeScript，無 UI 框架（介面 90% 是 canvas）。
相依：`rubberband-wasm`、`onnxruntime-web`。

### 檔案結構
```
src/
  audio/decode.ts        File → AudioBuffer；用 OfflineAudioContext 轉 16k mono 給偵測用
  audio/wav.ts           AudioBuffer → WAV Blob（匯出用）
  analysis/swiftf0.ts    Worker 裡跑 ONNX，回傳 {t[], f0Hz[], conf[], voiced[]}
  analysis/smooth.ts     移動中位數、unvoiced 區段內插
  model/curves.ts        Δ / G 曲線、格點換算、各種編輯運算
  model/project.ts       undo 堆疊、JSON 存讀
  engine/renderer.ts     Renderer 介面（將來要換神經聲碼器就從這裡換）
  engine/rubberband.ts   Rubber Band realtime 實作 + tile 快取
                         （可直接沿用 spike/rubberband-node.mjs 的驅動邏輯）
  view/waveform.ts       多層級 peak 快取，canvas 繪製
  view/pianoroll.ts      canvas：y = MIDI 音高、x = 時間；原始 f0（淡）+ 位移後 f0（亮）
  view/selection.ts      拖曳框選、上下拖曳手勢
  ui/app.ts              組裝、播放控制、滑桿面板
```

### 算繪策略：整段算繪一次 + 局部修補（spike 實測後簡化）

原本計畫的是「固定 1 秒 tile 網格」，實測之後改成更簡單的做法：

1. **載入時整段算繪一次**，存成一個與原檔等長的 buffer（100 秒約需 11 秒，有進度條）
2. **每次編輯只重算被改動的區域**（選取範圍 + 兩端斜坡 + 邊界餘裕），
   然後用 **25ms 交叉淡化**貼回那個 buffer
3. 播放就是播這個 buffer（單純的 `AudioBufferSourceNode`），零延遲

一段 2 秒的編輯只要重算約 0.25 秒，體感即時。不需要 tile 網格、不需要失效追蹤。

**前導暖機**：從中途開始算繪時要多讀一段前文（約 0.5 秒）讓相位聲碼器暖機，
算完丟掉。`renderWithCurve()` 的 `preRollSamples` 參數就是做這件事。

#### 交叉淡化是必要的，不是保險

實測接縫處的「相鄰 sample 跳躍量」（除以該處訊號 RMS，連續訊號的自然值約 0.45）：

| 接縫兩側的 Δ | 不淡化 | 5ms | 15ms | 30ms |
|---|---|---|---|---|
| 0 半音 | 0.25–0.34 ✅ | — | — | — |
| 3 半音 | **1.69 ❌** | 0.27 | 0.27 | 0.28 |
| 7 半音 | **2.46 ❌** | 0.19 | 0.20 | 0.22 |

相位聲碼器的輸出相位取決於整個處理歷史，所以分開算的兩段不可能相位一致——
Δ≠0 時接縫會是自然跳躍的 4–5 倍，那是聽得見的爆音。
但 5ms 淡化就壓下去了，15–30ms 連交叉區的梳狀抵消也消失（RMS 比 0.92→1.00）。
**採用 25ms。** 另外由於選取範圍的斜坡會讓 Δ 在邊界回到 0，
只要重算範圍涵蓋斜坡，接縫多半落在 Δ=0 的區域，本來就最安全。

#### 延遲補償（踩過的坑）

`renderWithCurve()` 只扣掉「自己餵進去的 start pad + preRoll」，
**不要**再扣 `rubberband_get_start_delay()`。用脈衝實測：不餵 pad 時輸出延遲是 0，
餵 2048 個靜音後延遲剛好 2048——Rubber Band 已經自己補償過演算法延遲了。
多扣一次會讓整段提早 2048 個 sample，而且不會報錯，只會聽起來對不上。

驗證：Δ 全為 0 時算繪輸出與輸入 lag = 0、相關係數 0.9975、RMS 相符。

### 時間基準（最容易出錯的地方）
偵測在 16 kHz / 16 ms 格點上，播放在原始取樣率。**所有內部時間一律用「秒」當基準**，只在顯示和送進算繪器時才換算。現有程式碼的註解（`pitchmark.py:157`）已經警覺到這類錯誤——不會報錯，只會聽起來很怪。

### 專案存檔
JSON：原始檔名 + 取樣率 + Δ 曲線 + G 曲線 + f0 分析快取（Float32 轉 base64）。
比照 `pitchmark.py:690` 的做法，載入時比對取樣率不符就拒絕載入。

### 實作過程中修正的兩個關鍵錯誤

1. **延遲補償多扣了一次**（見上方「延遲補償」）。
2. **復原無法完全還原**：交叉淡化的邊緣會永久保留一部分舊的算繪內容，
   實測殘留 1.1% RMS。修法是曲線回到中性時往外擴展到「整段連續中性」的最大範圍
   再從原始音訊複製，只在真正鄰接「仍有編輯」的地方才淡化。

- `npm run dev`，拖入音檔
- 波形和音高曲線要對得上：播放頭經過高音處，piano roll 的線要在高的位置
- 圈選一段拉高 2 個半音 → piano roll 的線跟著上移 2 格 → 播放聽起來高 2 個半音 → 邊界沒有「啵」聲
- **音色保留**：拉高 5 個半音，人聲聽起來要是「同一個人唱高音」，不是花栗鼠。把 `FormantPreserved` 關掉當對照組聽一次，差別要很明顯——如果關不關聽起來一樣，代表選項根本沒傳進去
- 壓平滑桿拉到 0 → 該段抖音消失變成直線，但如果選區內本來有滑音，滑音要還在
- 連續做 5 次編輯再全部 undo → 聲音要跟原始檔逐 sample 相同（證明沒有累積劣化）
- 匯出 WAV，長度與原檔一致，用其他播放器開起來正常
- 存檔後重新整理頁面再讀回 → 曲線與聲音完全一致

## 追加：時變音高曲線的三個坑（使用者回報「壓平抖音會斷斷續續」後查出來的）

第一版的壓平抖音功能在真實素材上不但無效，還會讓抖音變成原本的 140%。
查出來是三個獨立的問題疊在一起，每一個都足以讓功能失效。

驗證方法：合成一個「音高完全已知」的母音（穩定基頻 + 已知深度與頻率的抖音），
跑真正的產品程式碼（`edits.flattenRange` → `rbcore.renderWithCurve`），
再用 lock-in 量輸出的調變深度與相位。合成素材有 ground truth，
不必倚賴在真實素材上並不可靠的音高追蹤。

### 坑 1：`PitchHighQuality` 會把快速音高變化濾掉

輸出調變深度（Δ 曲線是 ±2 半音的正弦，完美跟隨 = 2.00）：

| 選項 | 1Hz | 2Hz | 3Hz | 5.5Hz | 8Hz |
|---|---|---|---|---|---|
| R3 + PitchHighQuality | 2.05 | 1.72 | 1.46 | **0.36** | 0.64 |
| R3 + **PitchHighConsistency** | 2.05 | 1.97 | 1.99 | **1.85** | 1.79 |

人聲抖音是 4~7Hz，正好落在壞掉的頻段。
（Rubber Band 文件說 R3 會忽略這組 pitch 選項——實測並沒有。）

### 坑 2：更新粒度是 85ms，但曲線是 16ms 一格

`rubberband_get_samples_required()` 回傳 4096（85.3ms），照這個粒度更新音高
等於把曲線降取樣 5.3 倍。跟隨深度：block 4096 → 1.32、1024 → **1.82**、512 → 1.85。
取 1024（21.3ms），品質與速度的平衡點。

曲線查詢也改成線性內插而非取最近的格子，否則延遲補償會被量化到 16ms。

### 坑 3：音高自動化比曲線早 85ms（最關鍵）

我們依照「剛讀進去的輸入位置」設定音高，但 Rubber Band 那一刻吐出來的輸出
對應的是更早的輸入。實測輸出的音高變化比曲線**早 85ms**，
而且 1~7Hz 量到的值完全一致（−84.5 / −84.6 / −85.0 / −85.1 / −85.1 / −85.2ms），
是個固定常數。

這對慢速編輯只是輕微不同步，但 5.5Hz 抖音的半週期是 91ms——幾乎等於 85ms，
**反向抵銷直接變成同向疊加**。補償後所有頻率的延遲降到 0.2~0.4ms。

補償值掃描（合成素材，α=0 完全壓平，數字是殘餘的抖音比例）：

| 補償 | 0ms | 40ms | 60ms | **85ms** | 100ms | 140ms |
|---|---|---|---|---|---|---|
| 殘餘 | **220%** | 151% | 89% | **21%** | 63% | 182% |

真實素材（`Vocal.wav` 66.4s，5.25Hz 抖音）的最終結果：

| 設定 | 壓平後的抖音 |
|---|---|
| 修正前 | 140%（變嚴重） |
| **修正後** | **8%** |
| α=0.5（半壓） | 53% |

三個修正都不影響音色保留（降調時還略好）、Δ=0 恆等性（lag 0、相關 0.9975）
與速度（6.5x 即時）。

### 驗收流程的教訓

原本的驗收量的是「曲線算出來的預期音高」，不是實際輸出的音高——
所以曲線明明對了、聲音卻沒被壓平，測試還是全綠。
現在 `npm run verify` 會多跑一個 `spike/flatten-truth.mjs`，
直接量算繪出來的聲音，門檻是殘餘抖音必須低於 35%。

## 追加：把上方軌做成 DAW 式的 Automation 區

第一版只有「音高」一個可編輯面向：音量藏在 footer 的滑桿裡，formant 只是算繪器
的常駐選項。使用者實際修音時回報的問題全都指向同一件事——**三個面向應該是同一套介面**。

### 三條 lane，一套操作

`Curves` 現在是三條每 16ms 一格的曲線，全部都是「加法語意 + 中性值 0」：

| lane | 欄位 | 單位 | 中性 | 顯示範圍 |
|---|---|---|---|---|
| 音高 | `pitch` | 半音 | 0 | 跟著 piano roll 的 MIDI 範圍 |
| 音量 | `gainDb` | dB | 0 | −24 … +12 |
| Formant | `formant` | 半音 | 0 | −12 … +12 |

語意統一之後，`shiftRange` / `gainRange` / `resetRange` 收斂成 `offsetLane` /
`resetLane` / `drawLane` 三個泛用函式，選取、垂直拖曳、畫筆、歸零各只要寫一次。

**gain 改存 dB 不是美學問題**：automation 線需要等距的刻度，而且「+3dB 再 +3dB」
在 dB 上是單純的加法，跟另外兩條 lane 一致。專案檔因此升到 v2，v1 讀入時
`gainDb = 20·log10(gain)`。

### 參數是活的（修掉「每動一次就疊加一次」）

舊版的滑桿在 `change` 時 `history.push` 然後把自己歸位，所以拉回 1.00× 不會回到原樣。
現在選取成立時凍結一份 `selBase`，**選取存在期間不更新**，所有面板參數都是從它
重新套用一次。回到中性值就逐位元等於 `selBase`。undo 每個「選取編輯階段」只結算一次。

同理，選取本身也要黏著：點選取範圍外面只移動播放頭，Esc 或重新拖曳才換掉。
舊版是「點一下就清掉選取」，等於逼使用者一次把參數調對。

### 邊界 ramp 可調，算繪餘裕要跟著動

`RAMP_SEC` 從模組常數變成每條 lane 各自的 `curves.rampSec`。
**`renderer.ts` 的 `MARGIN_SEC` 必須跟著變成 `max(rampSec) + 0.05`**——
ramp 拉長而餘裕不變的話，交叉淡化的接縫會落在 Δ≠0 的區域，就是本文件前面
量過的那種「自然跳躍量 4–5 倍」的爆音。

### Formant 的自動化延遲是 39ms，不是 85ms

音高自動化早了 85ms（見前面「坑 3」）。formant 走同一條相位聲碼器管線，
直覺上延遲應該相同——**實測不是**。`spike/formant-lag.mjs` 用頻譜包絡重心的
lock-in 量相位（f0 固定不動，只讓共振峰動）：

| 補償 | 1Hz | 2Hz | 3Hz | 5.5Hz |
|---|---|---|---|---|
| 不補償 | −39.2 | −39.3 | −39.4 | −39.9 ms |
| 補 85ms（照抄音高的） | +44.3 | +44.4 | +44.5 | +45.0 ms |
| **補 39ms** | **−0.9** | **−1.0** | **−0.9** | **−1.1 ms** |

跟頻率無關，是個固定常數，所以 `FORMANT_LAG_SEC = 0.039` 獨立於 `AUTOMATION_LAG_SEC`。
照抄 85ms 會補過頭 46ms：慢速編輯只是輕微不同步，但畫筆畫快一點就整個對不上。

對照組（formant 曲線全 0）量到的調變深度是 0.000 半音，確認指標沒有被別的東西汙染。

### 縱向導覽

第一版只有橫向視野（`ViewState`），piano roll 的縱軸是載入時用音高分位數算出來就
固定了，gain/formant 更是直接用 lane 的上下限——也就是根本沒有上下捲動這件事。

現在每條 lane 各有自己的**可視範圍**，跟 `LANES` 的 `min`/`max` 是兩回事：
那個是「值的上下限」（畫筆會夾），可視範圍則是「現在看得到哪一段」。
縱向的操作一律對**目前正在編輯的那條 lane** 作用。

滾輪照一般編輯器的慣例（`Shift` 代表「換成橫向」）：
單獨 = 縱向捲動、`Ctrl` = 縱向縮放、`Shift` = 橫向捲動、`Ctrl+Shift` = 橫向縮放。
波形軌沒有縱軸可言，所以在那裡一律當成橫向操作——不然在波形上滾滾輪會完全沒反應。
觸控板的橫向滑動（`deltaX`）不必按 `Shift` 也當成橫向。
另有兩支縮放滑桿，直接貼在軌道的右緣（縱向）與下緣（橫向），沒有裝在框裡——
這是常駐的控制項，加個底色方塊只會一直擋著曲線。平常淡淡的，滑鼠靠近才變明顯，
**雙擊還原**，所以也不用另外放還原鈕。代價是右緣那條 14px 的帶狀區域點不到 canvas，
所以做得盡量窄，lane 的刻度文字也往左讓開 22px。

縮放滑桿用**對數刻度**：從「100 秒塞滿」到「一個 sample 一個像素」跨了五個數量級，
線性刻度的話滑桿前 1% 就走完所有實用範圍。滑桿與視野**雙向同步**，
但正在拖滑桿時不同步，否則會跟使用者的手打架。

lane 的縱軸刻度間隔也跟著可視範圍走，放大時才看得到更細的格子。

縱向縮放的兩端要刻意選過：**縮到最小要比預設視野更寬**（音高是 5 個八度），
不然「縮小」根本沒得縮——預設視野是貼著素材音域算出來的，那本來就是很緊的框。
**放到最大則不必太細**：音高放到剩 4 個半音就足以看清抖音的形狀，再放大只是讓
曲線跑出畫面。滾輪與滑桿共用同一組上下限，不然兩種操作方式的可及範圍會不一樣。

### 修掉的一個老 bug：`[hidden]` 從來沒有生效

`footer#panel` 設了 `display: flex`，優先度高於 `[hidden]` 預設的 `display: none`，
所以 `<footer id="panel" hidden>` 一直都是看得到的——沒選取任何東西時也擺著一整排
「尚未選取」的滑桿。`main#stage` 也一樣（`display: grid`），還沒載入音檔就先看到空軌道。
補一條 `[hidden] { display: none !important; }` 解決。


### 其他

- **畫筆**（`B`）在作用中的 lane 上自由畫。音高 lane 畫的是絕對音高，存成相對於
  偵測值的偏移；未發聲的格子沒有基準可用，直接跳過。按住 Shift 吸附到整數半音。
- **Voice / Instrument 模式**（全域）：Voice = `r 0`，移調時保留音色；
  Instrument = `r 1`，音色完全跟著移調。中間的程度用 Formant 那條 lane 分段調，
  不再開連續旋鈕——這是會改變整個檔案聽感的設定，放在 header 而不是選取面板，
  做成兩顆按鈕而不是滑桿，免得被滑鼠掃到。會存進專案檔。換算公式見下一節。
- **畫筆的自動抖音**：幅度不為 0 時，畫出來的線會再加上 `A(t)·sin(2πft)`。
  三個細節都是踩過才知道的：
  - **相位一律用絕對時間算**。一次拖曳會產生幾十段 `penTo`，用筆畫相對時間的話
    每一段都從相位 0 重來，交界處就是一個突兀的跳動。
  - **幅度 A(t) 反過來要用「離落筆處多遠」算**，raised-cosine 漸入（預設 200ms）。
    真人的抖音是起音時幾乎沒有、然後才長出來的，一開始就滿幅度聽起來很機械。
    距離取絕對值，所以由右往左畫也一樣是從落筆處長出來。
  - **吸附（Shift）要在加抖音「之前」做**，否則抖音會被吸附整個抹掉。

  抖音與漸入各有一個勾勾（快速鍵 `V` 與 `Shift+V`——漸入是抖音的子選項，
  掛在同一個鍵上比另外找一個字母好記），抖音預設關閉。有了開關之後，
  幅度就不必再用 0 當「關閉」的代名詞——關掉時數值留著，下次打開就是上次的設定。
- **跟隨播放頭**（`F`）：做成「翻頁」而不是「一直把播放頭釘在中央」——連續捲動時
  曲線一直在動很難看清楚形狀，而且播放中手動捲去看別的地方會立刻被搶回來。
  播放頭跑到右側 85% 才翻一頁，讓它落在 15% 的位置。
- **算繪進度**：`renderWithCurve` 每 32 個 block 回報一次進度，經由 worker 傳回主執行緒。
  header 下方一條進度條，同時在兩個軌道上把「正在重算的時間範圍」標出來——
  一段長的畫筆或讀檔的整段重算要好幾秒，只有一行「算繪中…」的話，
  使用者分不出是在跑還是當掉了。
- **波形粗細**畫的是「原始峰值 × 目前的 gain 曲線」，不是算繪結果——
  算繪要等 500ms，但拖滑桿時使用者要「當下」就看到變化。
- 快捷鍵：`1/2/3` 切換編輯對象、`Shift+1/2/3` 切換顯示、`V/B` 工具、
  `L` 循環播放選取範圍、`F` 跟隨播放頭、`Esc` 取消選取、`Ctrl+Shift+Z` 重做。
  工具是 `S`（選取）與 `B`（畫筆），畫筆的抖音與漸入是 `V` 與 `Shift+V`。

### ⚠️ set_formant_scale(1.0) 不是「不動」——它會關掉音色保留

加入 formant 曲線時，「曲線值為 0 就傳 scale = 1.0」看起來理所當然，實際上是個
會讓**所有移調都變成花栗鼠**的 bug。舊版程式碼從來不呼叫 `set_formant_scale`，
它一直停在預設的 0.0（= 交給 `FormantPreserved` 自動推算）。

實測（`spike/formant-scale-semantics.mjs`，量頻譜包絡重心，保留率 1.0 = 完美保留）：

| 做法 | −5 | −2 | +2 | +5 | +7 | 平均 |
|---|---:|---:|---:|---:|---:|---:|
| 不呼叫（舊版） | 0.75 | 0.89 | 0.91 | 1.02 | 1.04 | **0.922** |
| 傳 0.0（auto） | 0.75 | 0.89 | 0.91 | 1.02 | 1.04 | **0.922** |
| 傳 1.0 | −0.01 | 0.05 | 0.00 | 0.03 | −0.00 | **0.014** ← 完全沒保留 |

**明確指定 scale 會關掉自動補償**，而且指定的值是相對於「已經移調後」的訊號：

```
實際的包絡位移（半音） = Δ + 12·log2(scale)
```

所以想要淨位移 D，要傳 `scale = 2^((D − Δ)/12)`，其中 Δ 是**這個 block 實際套用的
移調量**（不是 formant 延遲時刻的 Δ——那一項是在抵銷引擎當下的行為，不是使用者
看得到的量）。驗證這個公式（尺規是「把原始素材 resample D 半音」的包絡重心，
用 Δ 的校準去量 D 的位移會錯，這個指標在升降調方向上的壓縮率並不對稱）：

| Δ | D | scale | 量到 | 目標 | 誤差 |
|---:|---:|---:|---:|---:|---:|
| +7 | 0 | 0.667 | −0.19 | 0.00 | −0.19 |
| −5 | 0 | 1.335 | −0.56 | 0.00 | −0.56 |
| +7 | −4 | 0.530 | −1.57 | −1.77 | +0.20 |
| +2 | +2 | 1.000 | +1.18 | +1.18 | −0.00 |

誤差落在 Rubber Band 本身的音色保留精度內（本文件前面量到的平均 0.66 半音）。

**D = 0 時這個公式算出來就是 auto**：+7 兩者都是 −0.19、−5 兩者都是 −0.56，
逐項相同。所以不需要為「沒有 formant 編輯」另外開一條不呼叫的路徑，一條公式涵蓋
全部情況——也代表**使用者不必自己反向補償**，畫音高時音色保留是自動的。

這種錯誤不會當掉、不會有 console 錯誤、曲線也完全正確，只有「聽起來」不對，
所以 `npm run verify` 加了一支 `spike/formant-truth.mjs` 直接量產品路徑的輸出：
預設保留率須 > 0.80（實測 0.929），跟隨比例 1.0 須 < 0.15（實測 0.004），
還有 formant 曲線單獨與併同移調時包絡要落在該落的地方。

## 追加：起音處「沒被調到」、Δ 的抽動、音量延遲（polish）

### 起音那一下是曲線的問題，不是引擎的問題

使用者回報：把一段拉高很多時，「沒音高 → 有音高」那 ~10ms 聽起來像沒被調到。
`spike/onset-truth.mjs` 用合成素材（靜音 → 可選 30ms 子音雜訊 → 母音）量起音後每 1ms 的 f0 誤差：

| 情況 | 起音後 0–20ms 平均誤差 | 0–50ms |
|---|---:|---:|
| Δ = +7／+12 常數 | 0–1 cents | 0–1 |
| Δ 階梯剛好落在起音處、或提早 30ms | 1–2 | 1 |
| block 512／256、`OptionWindowShort` | 0–1（跟 1024 沒有差別） | 0–1 |
| **Δ 階梯晚 20ms（+7）** | **208** | 84 |
| **Δ 階梯晚 20ms（+12）** | **504** | 202 |

Rubber Band 在起音處完全跟得上，改 block 大小或視窗都沒有意義（所以沒有改）。
會重現問題的只有「Δ 到起音之後才跳上去」這個形狀——正是畫筆留下的：
畫筆以前遇到未發聲的格子就跳過，而 SwiftF0 的 voiced 門檻（confidence > 0.9）常把起音的前一兩格
（16–32ms）判成未發聲，那幾格的 Δ 就停在舊值。

修法：畫筆換算 Δ 時改用「未發聲空隙線性內插補滿」的偵測音高（`main.ts` 的 `pitchMidiFilled`，
重用 `edits.ts` 的 `fillGaps`），未發聲的格子也寫入。畫面仍然只畫發聲的格子。

選取工具（拖曳、滑桿、壓平）本來就對未發聲格子寫入連續的 Δ，沒有這個問題。

### Δ 變化率上限

原唱本身有一個很陡的音高變化（換音），使用者把它修平，Δ 在那裡就是陡的階梯，
Rubber Band 每 21ms 換一次倍率，聽起來是一下抽動。`edits.ts` 的 `limitSlope` 把 Δ 限制在
每秒最多 L 半音（`Curves.pitchSlopeLimit`，預設 60，footer 可調，0 = 不限制，存進專案檔）。

演算法是上下兩條 Lipschitz 包絡取平均（O(n)）：
- 本來就合乎限制的曲線**逐位元不變**，所以「滑桿拉回中性就逐位元還原」仍然成立
- 階梯變成以原位置為中心、總長 2S/L 的斜坡（+1 半音 ≈ 33ms，+12 半音 ≈ 400ms）
- 結果的斜率一定 ≤ L

60 的理由：深 1 半音、6Hz 的抖音峰值斜率 37.7 半音/秒，壓平與畫筆抖音都不受影響；
`spike/flatten-truth.mjs` 套上限制後殘餘抖音 4%（門檻 35%）。

套用點：拖曳與滑桿每次重套時、歸零之後、畫筆**放開時**（畫的途中每小段都套的話，
已經畫好的部分會被反覆抹平）。限制器會把編輯往外推，所以重算範圍改成
「選取範圍 ∪ 曲線實際改到的範圍」（`main.ts` 的 `editRange`），否則接縫會落在 Δ≠0 處。

`spike/slope-limit-test.mjs` 驗這些性質。

### 音量晚了 85ms

以前增益乘在餵進 Rubber Band 的**輸入**上，還用扣掉音高自動化延遲的時間去查曲線。
但乘在輸入上的增益會跟著訊號走完整條管線，而管線延遲 Rubber Band 已經自己補償了——
所以 85ms 的補償是多扣的。`spike/gain-lag.mjs`（±6dB 正弦音量、量輸出 RMS 與曲線的最佳對齊）：

| | 1Hz | 2Hz | 4Hz |
|---|---:|---:|---:|
| 修正前，不移調 | 晚 85ms | 晚 85ms | 晚 85ms |
| 修正前，+7 | 晚 70ms | 晚 70ms | 晚 71ms |
| **修正後** | **0ms** | **0ms** | **0ms** |

現在增益乘在**輸出**上（`rbcore.ts` 的 `applyGain`，每 64 sample 查一次曲線、中間內插），
沒有延遲、沒有 21ms 的階梯，也不會讓 Rubber Band 把音量變化當成 transient。

連帶的：只有音量編輯（音高與 formant 都是 0、沒有伸縮）的段落不再送進 Rubber Band，
直接「原始音訊 × 增益」貼回（`renderer.ts` 的 `pasteOriginal`）。純音量編輯變成即時，
而且不會因為重新合成損失原音（0 半音的 Rubber Band 相關係數只有 0.9975）。

### dual-mono 只算一個聲道

每個聲道逐 sample 相同的檔案（`Vocal.wav` 就是）只送一個聲道進 Rubber Band，結果複製到所有聲道。
算繪時間減半，也不會有兩個聲道各自走出不同相位的問題。

真立體聲的 `OptionChannelsTogether` 沒有採用：手上沒有立體聲人聲素材可以量音色保留與壓平效果，
不能確認不退步。
